# Internationalization (i18n) — Web

`apps/web` uses **react-i18next**; user-visible copy should be driven by translation keys, keeping the Chinese and English resources aligned.

## Resource files

- Chinese: `apps/web/src/locales/zh.json`
- English: `apps/web/src/locales/en.json`

**The same set of keys must be maintained in both files** (when adding a key, write it in both; when deleting or renaming, sync both sides). Avoid changing only one language, which causes runtime missing keys or improper fallback.

## Code usage

- Inside a React component: `useTranslation()` → `t('some.key')`.
- In non-component modules (such as entry-point error messages): `i18n.t(...)` (see existing usage in `main.tsx`, etc.).

**Do not** hardcode full user-facing Chinese/English sentences in JSX, unless there is already a project-agreed exception (e.g. a purely dev-facing placeholder, or a verbatim third-party quote); new features go through i18n by default.

## Ant Design language pack

`app.tsx` selects `zh_CN` / `en_US` based on `i18n.language` and passes it to `ConfigProvider`'s `locale`, consistent with the interface copy language. When adding a page that relies on antd copy, there is no need to repeatedly set the locale in each component.

## Interop with E2E

- When modifying **routes, navigation, page structure** or **i18n copy** (especially the sidebar `nav`, etc.), you must sync-update the relevant cases under `e2e/`.
- Keep assertion copy for navigation etc. consistent with `nav` in `zh.json` (or the display in the language selected by the test); shared constants go in `e2e/utils/test-constants.ts`.

## Initialization config

Logic entry: `apps/web/src/i18n.ts` (`fallbackLng`, resource registration, etc.). When changing the default language or namespace, evaluate whether the settings page's `useLocale` and user preference storage remain consistent.
